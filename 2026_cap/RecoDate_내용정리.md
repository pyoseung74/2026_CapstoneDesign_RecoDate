# RecoDate MVP 인수인계 문서

## 1. 앱 소개

RecoDate는 강릉 데이트 코스를 자동으로 추천하는 웹·모바일 MVP입니다.

사용자가 추천 지역, 시작 장소, 이동수단, 식사 여부, 숙박 여부, 꼭 들를 장소 등을 선택하면 음식점, 카페, 야외 액티비티, 실내 액티비티, 문화/전시, 마무리/산책, 술집 등을 조합하여 하루 데이트 코스를 추천합니다. 추천된 코스는 사용자가 직접 장소를 변경, 삭제, 추가, 순서 변경할 수 있고 최종 코스를 저장하거나 공유할 수 있습니다.

이 앱의 핵심은 업종 중심 추천이 아니라 데이트 안에서의 장소 역할을 기준으로 코스를 구성한다는 점입니다.

## 5. 장소 역할 분류

장소는 업종명이 아니라 데이트 코스 안에서의 역할로 나눕니다.

```text
01 전체
02 음식점
03 카페
04 야외 액티비티
05 실내 액티비티
06 문화/전시
07 마무리/산책
08 술집
```

자동 코스 추천과 자동 장소 변경에서는 아래 세 가지를 놀거리 묶음으로 함께 봅니다.

```text
야외 액티비티
실내 액티비티
문화/전시
```

다만 Choose Category 화면에서는 세 카테고리를 합치지 않고 각각 분리해서 보여줍니다.

예시:

```text
안목해변 -> 야외 액티비티
CGV 강릉 -> 실내 액티비티
강릉시립미술관 -> 문화/전시
아르떼뮤지엄 -> 문화/전시 또는 실내 액티비티
아쿠아리움 -> 실내 액티비티 또는 문화/전시
```

## 7. 로그인 화면

현재 첫 접속 흐름:

- 로그인 상태가 없으면 로그인 화면이 먼저 표시됩니다.
- 로그인 상태가 유효하면 메인 화면으로 복원됩니다.
- 로그아웃하면 메인 화면이 아니라 로그인 화면으로 이동합니다.

로그인 화면 개선:

- 로그인 화면 중앙 상단에 큰 Rec♡Date 로고 추가
- 기존 문구와 겹치지 않도록 상단 여백 조정
- 로그인 상태 유지하기 체크박스 추가
- 비밀번호 보기 눈 버튼 추가

로그인 유지 정책:

- 로그인 상태 유지하기를 체크하면 토큰을 localStorage에 저장합니다.
- 체크하지 않으면 토큰을 sessionStorage에 저장합니다.
- 체크하지 않은 사용자는 브라우저를 완전히 닫고 다시 열면 다시 로그인해야 합니다.
- 기존에 저장된 옛 토큰은 유지 선택 정보가 없으면 세션 저장 방식으로 전환됩니다.

## 8. 회원가입과 계정 정책

회원가입 기능:

- 아이디
- 이메일
- 전화번호
- 닉네임
- 비밀번호

정책:

- 전화번호 필수
- 아이디 중복 차단
- 이메일 중복 차단
- 전화번호 중복 차단
- 신규 비밀번호는 8자 이상
- 신규 비밀번호는 특수문자 1개 이상 포함
- 이메일은 소문자로 정규화
- 전화번호는 숫자만 저장
- 기존 가입자는 예전 비밀번호 규칙과 빈 전화번호 상태로도 로그인 가능

보안 구현:

- SQLite users 테이블에 phone 컬럼 추가
- 빈 전화번호를 제외한 phone 고유 인덱스 생성
- 백엔드 Pydantic 스키마에서 신규 가입 입력값 검증
- 프론트에서도 전화번호와 비밀번호를 사전 검증
- 로그인과 회원가입 비밀번호 칸에 보기/숨기기 버튼 추가

주의:

현재는 같은 전화번호 중복 가입을 막는 방식입니다. 실제 사람 기준 1인 1계정을 강하게 보장하려면 SMS 인증번호 확인 기능이 필요합니다.

## 11. 장소 사진과 리뷰

적용 및 조사 내용:

- Google Maps Platform에서 가능한 장소 사진과 리뷰 수 활용
- Google 리뷰 수를 추천 우선순위와 장소 탐색 정렬에 반영
- 관광지, 산책, 문화 장소는 한국관광공사 관광사진 API 활용 방향으로 구성
- 음식점과 카페는 Google Places Photos API 활용
- 사진을 가져오지 못한 장소에는 임의 생성 이미지를 넣지 않음
- 저작권 문제가 생길 수 있는 무단 이미지 수집은 사용하지 않음

권장 출처:

```text
관광지·산책·문화 장소 -> 한국관광공사 TourAPI 관광사진 API
음식점·카페 -> Google Places Photos API
리뷰 수·평점 -> Google Places Details API
```

- 음주를 선택하면 마지막 코스에 술집이 추가됩니다.
- 점심을 먹지 않으면 식당 없이 활동, 카페, 활동 중심으로 구성할 수 있습니다.

## 19. 발표 실행 방법

가장 쉬운 방법:

## 추가 정리: Google Places 데이터 캐싱과 로딩 속도 개선

2026-06-03 기준으로 Google 공식 문서를 확인한 결과, Places API로 받은 모든 데이터를 우리 DB에 마음대로 장기 저장해 두고 주 1회 갱신하는 방식은 권장하지 않는다.

Google Places API 정책상 주의할 점:

- Places API 콘텐츠는 허용된 예외를 제외하고 사전 수집, 캐시, 저장하면 안 된다.
- `place_id`는 캐싱 제한 예외이므로 장기 저장할 수 있다.
- Google은 Place ID가 바뀔 수 있으므로 12개월이 넘은 Place ID는 갱신할 것을 권장한다.
- Places API의 위도와 경도는 최대 30일 동안 임시 캐시할 수 있다.
- 사진, 리뷰 수, 평점, Google Maps 링크, 출처 정보 등은 표시 시 Google Maps attribution과 제공자 attribution을 유지해야 한다.
- Google Places 결과를 표시할 때는 Google Maps 제공 콘텐츠임을 명확히 표시해야 한다.

공식 근거:

- Google Places API 정책: https://developers.google.com/maps/documentation/places/web-service/policies
- Google Place ID 저장과 갱신: https://developers.google.com/maps/documentation/places/web-service/place-id
- Google Maps Platform Service Specific Terms: https://cloud.google.com/maps-platform/terms/maps-service-terms

따라서 RecoDate에서 안전하게 쓸 수 있는 속도 개선 방향은 다음과 같다.

1. 자체 장소 DB 구축

   장소명, RecoDate 내부 카테고리, 지역, 좌표, 설명, 가격대, 추천 태그 등은 Google에서 가져온 데이터가 아니라 자체 조사 데이터 또는 공공데이터 기반으로 구축한다.

2. Google place_id만 장기 저장

   각 장소에 Google `place_id`를 연결해 둔다. 이후 화면 표시가 필요할 때 Google Places Details 또는 Photos API로 최신 리뷰 수, 평점, 사진 메타데이터를 가져온다.

3. 짧은 서버 캐시 사용

   같은 사용자가 같은 지역/카테고리를 반복해서 누를 때를 대비해 서버 메모리 또는 SQLite에 짧은 TTL 캐시를 둘 수 있다. 다만 Google 콘텐츠는 정책을 보수적으로 적용해 장기 저장하지 않는다.

4. 페이지 단위 로딩 유지

   `Choose Category`의 전체 카테고리는 한 번에 100개를 가져오지 않고 `count=12`, `offset=0`부터 시작한다. 더보기 클릭 시 `offset=12`, `offset=24`처럼 다음 12개를 새로 요청한다.

5. Google API 호출 최소화

   첫 화면에 필요한 12개만 Google 보강을 수행하고, 사용자가 더보기를 누를 때 다음 12개만 추가로 보강한다. 화면에 보이지 않는 장소 사진과 리뷰를 미리 대량으로 가져오지 않는다.

6. 관광지 사진은 TourAPI 우선

   관광지, 산책, 문화/전시 장소는 한국관광공사 TourAPI 관광사진 API를 우선 사용한다. 음식점과 카페만 Google Places Photos API에 의존하는 방식이 비용과 정책 측면에서 더 안전하다.

7. 추천 결과는 자체 점수 + 최신 Google 보강

   추천 후보 자체는 RecoDate 자체 DB와 거리 계산으로 빠르게 만들고, 최종 화면에 보이는 장소에 대해서만 Google 리뷰 수와 사진을 보강한다.

현재 반영된 로딩 개선:

- `/api/places/browse`에 `count`와 `offset`을 적용했다.
- 첫 요청은 `count=12&offset=0`으로 12개만 가져온다.
- 더보기 클릭 시 `count=12&offset=12`처럼 다음 12개를 새로 요청한다.
- 기존처럼 서버에서 100개를 한 번에 가져온 뒤 프론트에서 12개씩 잘라 보여주는 방식이 아니다.
- 실제 검증 결과 전체 카테고리 첫 요청은 12개, 더보기 후 24개 표시로 동작했다.

## 추가 정리: TripTI 여행 취향 테스트

RecoDate에 여행/데이트 취향 테스트 기능인 `TripTI`를 추가했다. 일반 MBTI처럼 성격을 분류하는 기능이 아니라, 여행과 데이트 코스 취향을 4개 축으로 나누는 기능이다.

TripTI 축:

- H / T: 힐링형 / 관광형
- C / A: 차분형 / 액티브형
- P / F: 계획형 / 즉흥형
- S / E: 감성형 / 경험형

구성:

- 상단 메뉴에 `TripTI` 버튼 추가
- 별도 TripTI 화면 추가
- 15개 질문을 A/B 선택형 카드로 표시
- 답변 진행률 표시
- 15문항을 모두 선택하면 결과 코드와 유형 이름 표시
- 결과는 `H-A-P-E`처럼 4개 축 코드로 표시
- 결과 이름, 설명, 추천 흐름 표시
- 결과는 브라우저 `localStorage`에 저장되어 같은 브라우저에서 다시 확인 가능
- `다시 하기`로 답변과 결과 초기화 가능
- `TripTI로 코스 추천받기` 버튼을 누르면 RecoDate 추천 조건 화면으로 이동하고, TripTI 결과에 맞춰 일부 추천 조건을 자동 반영

TripTI 추천 조건 반영 기준:

- 액티브형(A)이면 이동수단을 대중교통 중심으로 설정하고 이동 반경을 넓게 잡는다.
- 차분형(C)이면 도보 중심, 짧은 이동 반경으로 설정한다.
- 힐링형(H)은 비교적 여유로운 경유지 개수로 설정한다.
- 관광형(T)은 더 많은 경유지를 둘러보는 방향으로 설정한다.
- 계획형(P)은 오전 시작 시간 기준으로 설정한다.

- 감성형(S)은 카페/숙박 같은 분위기 중심 옵션을 우선 살린다.

### TripTI 결과 화면 개선

TripTI 결과 표시 방식을 수정했다.

- `결과 보기`를 누르면 질문 목록 아래에 결과가 붙는 방식이 아니라, 질문 화면이 사라지고 결과 전용 화면만 보이도록 변경했다.
- 사용자가 결과를 받은 뒤 메인 화면으로 나갔다가 다시 `TripTI`에 들어오면 저장된 결과 화면만 바로 표시된다.
- `다시 하기`를 누르면 저장된 결과를 삭제하고 15개 질문 화면으로 돌아간다.
- 점수는 `힐링 H 3 / 관광 T 1` 같은 카운트 문구 대신 퍼센트로 표시한다.
- 각 축은 한 줄 단위로 표시한다.
  - 힐링 / 관광
  - 차분 / 액티브
  - 계획 / 즉흥
  - 감성 / 경험
- 각 축마다 둥근 가로 막대 그래프를 표시한다.
- 왼쪽 성향은 노란색, 오른쪽 성향은 하늘색으로 비율이 채워지게 했다.
- 결과 화면이 허전하지 않도록 저작권 문제 없는 자체 SVG 여행 캐릭터 일러스트를 추가했다.
- 유형 성향에 따라 일러스트 안의 `SLOW / ACTIVITY`, 별/하트 포인트, 배경색이 다르게 보이도록 구성했다.
- 홈 화면의 큰 `RecoDate` 추천 버튼 아래에 `내 여행 유형 확인하기 TripTI` 카드와 버튼을 추가했다. 사용자는 상단 메뉴뿐 아니라 메인 화면에서도 TripTI로 바로 진입할 수 있다.
- TripTI 질문 화면에서는 `다시 하기` 버튼을 제거하고 `결과 보기` 버튼만 남겼다.
- TripTI 질문 진행도 바는 `position: sticky`로 설정하여 질문을 아래로 스크롤해도 상단에 고정되어 계속 볼 수 있게 했다.
- TripTI 질문 화면의 `메인 화면으로 돌아가기` 버튼도 진행도 바와 함께 sticky 처리했다. 스크롤 시 상단에는 `메인 화면으로 돌아가기` 버튼이 먼저 보이고, 그 아래에 진행도 바가 따라온다.
- TripTI 결과 화면에서 `다시 하기`를 눌러도 기존 결과를 즉시 삭제하지 않도록 수정했다. 새 질문을 끝까지 완료하고 `결과 보기`를 눌렀을 때만 결과가 새 값으로 교체된다. 다시 하기 도중 메인 화면으로 나가면 기존 결과가 그대로 유지된다.
- RecoDate 추천 조건 화면에 `TripTI 결과 적용` 체크박스를 추가했다. RecoDate 버튼을 눌러 들어왔다고 해서 TripTI 결과가 무조건 적용되지는 않고, 사용자가 이 체크박스를 선택했을 때만 TripTI 결과가 추천 조건에 반영된다.
- TripTI 결과가 없는 사용자는 `TripTI 결과 적용` 체크박스를 선택할 수 없고, 회색 비활성 상태와 `TripTI 결과를 받은 뒤 선택할 수 있어요.` 안내가 표시된다.
- TripTI 결과가 있는 사용자는 체크박스를 켤 수 있으며, 체크 시 상세 설정, 이동수단, 이동 반경, 경유지 개수, 숙박/식사 옵션 등이 TripTI 유형에 맞게 채워진다.

## 추가 정리: 찜한 장소 선택 추천

찜 기능을 수정했다. 기존에는 사용자가 찜한 모든 장소를 한 번에 코스 추천에 넣을 수 있어, 서로 너무 멀거나 성격이 다른 장소가 섞이면 추천이 어색해질 수 있었다.

현재 방식:

- 찜은 기존처럼 장소 저장 목록 역할을 한다.
- 찜한 장소 중 코스 추천에 넣고 싶은 장소만 체크박스로 선택한다.
- `찜` 화면의 버튼 문구는 `선택한 장소 N개로 코스 추천받기`로 표시된다.
- 아무 장소도 선택하지 않으면 버튼은 비활성화되고 `장소를 선택해 주세요`로 표시된다.
- 선택된 장소만 `required_places`로 추천 요청에 전달된다.
- 장소 탐색 화면의 하단 찜 트레이도 체크 가능한 칩 형태로 바뀌었고, 여기서도 선택한 장소만 추천에 사용된다.
- 찜한 장소를 삭제하면 해당 장소의 선택 상태도 함께 제거된다.

검증 결과:

- 찜한 장소가 없으면 찜 화면은 빈 목록으로 표시된다.
- 장소를 찜하면 찜 화면에 카드가 생성되고 기본 상태는 미선택이다.
- 체크 전 추천 버튼은 비활성화된다.
- 체크 후 카드가 선택 상태로 표시되고 `선택한 장소 1개로 코스 추천받기` 버튼이 활성화된다.

## 추가 정리: 추천 결과 저장 및 내 코스 상세 재열기

추천 결과 카드의 저장 기능을 개선했다.

- 추천 결과 카드 안의 `코스 저장` 버튼 문구를 `결과 저장하기`로 변경했다.
- `결과 저장하기`를 누르면 해당 추천 코스가 `내 코스`에 저장된다.
- 저장 직후 자동으로 `내 코스` 화면으로 이동한다.
- `내 코스`에는 저장한 여러 코스가 카드 형태로 누적된다.
- 저장된 코스 카드를 누르면 RecoDate 추천 결과 화면처럼 해당 코스가 다시 열린다.
- 저장된 코스를 다시 연 화면에서도 기존 추천 결과 카드와 동일하게 장소 목록, 예산, 거리, 점수, 장소 변경/삭제/추가, 공유, 저장 버튼을 볼 수 있다.
- 저장된 코스 카드를 다시 연 뒤 코스 카드를 누르면 `코스 흐름` 화면으로 이동한다.
- 코스 흐름 화면에서는 기존과 같이 네이버 지도 `전체 코스 길안내` 버튼을 사용할 수 있다.
- 저장된 코스의 공유/삭제 버튼은 카드 열기 동작과 충돌하지 않도록 분리했다.

- 저장된 코스 카드 1개 생성 확인
- 저장된 코스 카드 클릭 시 추천 결과 화면 형태로 재오픈 확인
- 재오픈된 코스 카드 클릭 시 `코스 흐름` 화면 이동 확인
- 코스 흐름에서 네이버 `전체 코스 길안내` 버튼 표시 확인

## 추가 정리: 시작 장소 선택 창 개선

RecoDate 추천 조건 화면의 시작 장소 선택 방식을 개선했다.

기존에는 시작 장소 입력창에서 바로 검색 결과가 아래에 표시되는 구조였지만, 사용자가 요청한 참고 영상 흐름에 맞춰 `검색` 버튼을 누르면 별도 선택 창이 열리도록 변경했다.

현재 방식:

- 추천 조건 화면에서 시작 장소 입력 후 `검색` 버튼을 누르면 `시작 장소 선택` 모달이 열린다.
- 모달 안에는 검색어 입력창, 검색 버튼, 검색 후보 지도 영역, 후보 장소 목록이 함께 표시된다.
- 모달 검색은 기존 백엔드 장소 검색 API인 `/api/places/search`를 사용한다.
- 검색 후보는 최대 7개까지 표시되며, 후보 장소를 누르면 시작 장소로 선택된다.
- 후보 지도는 별도 지도 SDK를 새로 붙이지 않고, 검색 결과 좌표를 바탕으로 간단한 SVG 지도형 미리보기로 구성했다.
- 후보 지도 안의 번호 마커를 눌러도 해당 장소를 시작 장소로 선택할 수 있다.
- 시작 장소를 선택하면 추천 조건 화면의 시작 장소 상태가 즉시 갱신되고, 모달은 자동으로 닫힌다.
- 시작 장소는 여전히 선택사항이다. 사용자가 선택하지 않으면 기존처럼 시작 장소 없음 상태로 추천을 받을 수 있다.

구현 파일:

- `frontend/index.html`: `startPlaceModal`, `startPlaceModalKeyword`, `startPlaceCandidateMap`, `startPlaceModalResults` 추가
- `frontend/app.js`: `openStartPlaceModal()`, `closeStartPlaceModal()`, `searchStartPlacesInModal()`, `renderStartPlaceModalResults()`, `renderStartPlaceCandidateMap()`, `selectStartPlaceFromModal()` 추가
- `frontend/styles.css`: 시작 장소 모달, 후보 지도, 후보 장소 카드 스타일 추가
- `mobile/web`, `android/app/src/main/assets/public`, `ios/App/App/public`: `npm run mobile:sync`로 모바일 앱 소스에도 동기화 완료

검증 상태:

- `node --check frontend/app.js` 문법 검사 통과
- 현재 백엔드 서버가 `127.0.0.1:8010`에서 실행 중이 아니어서 실제 장소 검색 API 응답은 이 시점에서 확인하지 못했다.
- 백엔드를 실행한 뒤 웹에서 `RecoDate` 버튼 클릭 → 시작 장소 검색 → 모달에서 `강릉역` 검색 → 후보 장소 선택 순서로 확인하면 된다.

### 시작 장소 선택 창 추가 개선

사용자가 원한 지도 형태가 단순 SVG 미리보기가 아니라 실제 TMAP 배경지도였기 때문에 시작 장소 선택 모달의 지도 영역을 다시 개선했다.

- 시작 장소 검색 후보 지도는 TMAP JavaScript SDK 기반의 실제 지도 컨테이너로 표시된다.
- 검색 후보 장소 좌표에 번호 마커를 표시한다.
- TMAP SDK 로딩이 실패하면 기존 TMAP Static Map 이미지를 사용하는 예비 화면으로 전환한다.
- 후보 장소 목록 왼쪽에는 장소 사진 썸네일 영역을 추가했다.
- 후보 사진은 Google Places Photo 검색 결과를 사용하며, 사진이 없거나 아직 로딩 중이면 번호 배지만 유지된다.
- 추천 결과 사진, 시작 장소 후보 사진, 코스 흐름 장소 사진이 같은 프론트 사진 메타데이터 캐시를 공유하도록 보강했다.
- 추천 결과 사진이 느린 이유는 처음 보는 장소의 경우 `Google 사진 메타데이터 검색 → 실제 이미지 요청`의 2단계 요청이 필요하기 때문이다. 캐시가 쌓이면 같은 장소 재표시는 더 빨라진다.
- 코스 흐름 화면의 장소 카드에도 각 장소 사진 썸네일을 추가했다.

구현 파일:

### 서버 계정별 TripTI 저장 / 추천 결과 조작 UX 보강

- TripTI 결과를 브라우저별 localStorage 저장이 아니라 서버 사용자 DB에 저장하도록 변경했다.
- `users` 테이블에 `tripti_result` 컬럼을 추가하고, 로그인 사용자별 TripTI JSON을 저장한다.
- `/api/auth/me` 응답에 `tripti_result`가 포함되어 같은 계정이면 다른 브라우저에서 로그인해도 기존 TripTI 결과를 이어서 볼 수 있다.
- `/api/auth/tripti-result` GET/POST API를 추가해 TripTI 결과를 계정 단위로 조회/저장한다.
- 다른 계정으로 로그인하면 해당 계정의 TripTI만 보이며, 이전 브라우저에 남은 다른 사람의 TripTI가 섞이지 않는다.
- 상단 마이페이지 버튼의 닉네임 뒤 `?` 표시를 `님`으로 수정했다.
- 안목·송정 실내 액티비티처럼 지역 결과가 없을 때 `강릉 전체로 다시 보기`를 누르면 같은 카테고리인 `강릉 전체 실내 액티비티`로 확장 조회된다.

### TripTI 5축 / 32유형 데이터 개편

- TripTI 질문지를 새 5축 구조로 변경했다.
- 새 축은 `휴양 R / 관광 T`, `느긋 L / 부지런 B`, `계획 P / 즉흥 F`, `실용 U / 감성 S`, `핫플 H / 로컬 O`이다.
- 기존 4축 16유형 구조였던 `H/T`, `C/A`, `P/F`, `S/E` 계산식을 5축 32유형 구조로 교체했다.
- 질문은 사용자가 유형 축을 쉽게 눈치채지 못하도록 축별로 묶어 보여주지 않고, `R/T → L/B → P/F → U/S → H/O` 흐름이 반복되도록 섞었다.
- 첨부된 TripTI 32개 유형명, 핵심 설명, 추천 흐름을 결과 화면 데이터로 모두 반영했다.
- 결과 화면은 `R-L-P-U-H : 실속 핫플 휴양러`처럼 5글자 코드와 유형명을 보여주고, 각 유형 설명과 추천 흐름을 함께 표시한다.
- 결과 그래프도 기존 4개 축에서 5개 축으로 변경해 `휴양/관광`, `느긋/부지런`, `계획/즉흥`, `실용/감성`, `핫플/로컬` 비율을 퍼센트 막대로 보여준다.
- 기존 브라우저나 계정에 남아 있던 4축 TripTI 결과는 새 32유형에 없는 코드이므로 무시하도록 처리했다.

TripTI가 코스 추천에 반영되는 방식:

- TripTI는 추천조건 화면에서 사용자가 `TripTI 적용`을 체크했을 때만 반영된다.
- TripTI 결과가 없는 사용자는 체크박스가 비활성화된다.
- TripTI는 식사 여부, 저녁 여부, 숙박 여부, 술집 추가, 이동수단을 강제로 바꾸지 않는다.
- 상세설정에서는 TripTI에 따라 경유지 수를 보조 조정한다.
- 관광형 또는 부지런형이면 더 알찬 코스를 위해 경유지 수를 늘리고, 휴양형 또는 느긋형이면 부담을 줄이기 위해 경유지 수를 줄인다.
- 이동 반경도 관광형 또는 부지런형은 넓게, 휴양형 또는 느긋형은 좁게 잡는다.
- 장소 카테고리는 TripTI 결과에 맞는 후보를 우선 정렬한다.
- 휴양/느긋 성향은 카페, 마무리/산책, 문화/전시를 우선한다.
- 관광/부지런 성향은 문화/전시, 야외 액티비티, 실내 액티비티를 우선한다.
- 감성/핫플 성향은 사진과 분위기가 강한 문화/전시, 액티비티, 카페를 우선한다.
- 로컬 성향은 마무리/산책, 카페, 문화/전시처럼 비교적 부담 없는 장소를 우선한다.
- 단, TripTI 카테고리는 강제 필터가 아니라 우선순위이다. 조건에 맞는 장소가 부족하면 기존 추천 로직대로 다른 카테고리 후보를 채워 코스가 끊기지 않게 한다.

### 디자인 정리 / 장소 카테고리 / 최신 수정 사항

- 전체 디자인은 기존 핑크·민트 색감을 유지하면서 카드, 버튼, 입력창, 추천 결과 화면을 더 둥글고 깔끔한 톤으로 정리했다.
- 추천 조건 화면의 시작 장소 선택, 지역 선택, 시간 선택, TripTI 적용, 상세 설정 UI를 더 귀엽고 읽기 쉬운 형태로 다듬었다.
- 추천 결과와 코스 흐름 화면은 장소 사진, 리뷰 배지, 네이버 검색 버튼, 코스 저장 버튼을 함께 볼 수 있게 구성했다.
- 음식점 카테고리는 `한식`, `중식`, `일식`, `양식`, `패스트푸드`, `기타(쌀국수, 인도음식 등)` 기준으로 정리했다.
- `steak_house`는 양식, `bakery`는 카페, `meal_takeaway`처럼 애매한 음식 분류는 기타 또는 전문음식점 계열로 처리하도록 정리했다.
- 자차 이동 시 추천 반경은 최대 20km까지 허용하되, 프로토타입 범위는 강릉 안으로 제한했다.
- 대중교통 이용 시 짧은 도보 구간은 도보로 처리하고, 편도 도보 이동이 너무 길어지지 않도록 10분 이내 기준을 반영했다.
- 추천 결과의 장소 변경 후보에도 Google 리뷰 수와 네이버 리뷰순 순위가 보이도록 했다.
- Explore Gangneung 장소 목록은 필터된 장소 안에서 네이버 지역 검색 API의 리뷰순 순위를 우선 적용하고, Google 리뷰 수는 보조 정보로 유지한다.
- Explore Gangneung 로딩 속도 개선을 위해 Google Places 결과를 병렬로 먼저 사용하고, 부족한 장소는 느린 TMAP 보강 대신 로컬 안전망으로 즉시 채우도록 변경했다. 장소 목록 캐시는 1시간 유지한다.
- 프론트에서도 Explore Gangneung 장소 목록을 브라우저에 캐시해 두고, 같은 지역/카테고리를 다시 열면 저장된 네이버 리뷰순 결과를 먼저 보여준 뒤 최신 API 결과로 자동 갱신한다.
- Explore Gangneung 목록은 로딩 속도를 위해 사진을 제외하고 장소명, 카테고리, 리뷰 수, 찜, 검색 버튼만 먼저 보여준다. 장소 카드를 클릭하면 상세창에서 TMAP 지도와 장소 사진을 로드하며, 사진은 네이버 이미지 검색 API를 우선 사용하고 실패 시 Google 사진을 보조 fallback으로 사용한다.
- Explore Gangneung의 `전체` 카테고리는 Google Places Nearby API의 단일 요청 20개 제한에 막히지 않도록 장소 타입별 Google 검색과 TMAP 지역·카테고리·페이지 검색을 병렬로 수행한 뒤 중복 제거와 네이버 리뷰순 정렬을 적용한다. 강릉 전체/전체 기준 첫 수집 약 2.83초, 총 732개, 12개씩 61페이지까지 더보기가 이어지는 것을 확인했다.
- 장기적으로 방대한 장소 DB를 만들려면 한국관광공사 `국문 관광정보 서비스_GW`의 지역기반/위치기반/키워드/공통정보/소개정보/이미지정보를 주기적으로 수집해 SQLite 또는 별도 DB에 적재하고, Google 리뷰 수와 네이버 순위는 화면 표시 또는 주기 업데이트용 보강 데이터로 사용하는 구조가 적합하다.
- 한국관광공사 `국문 관광정보 서비스_GW` 승인이 API 게이트웨이에 반영되어 강릉 관광정보 832개를 `backend/data/recodate_places.db`에 적재했다. 프로젝트 루트에서 `cd backend` 후 `python scripts/sync_tour_places.py`를 실행하면 최신 데이터로 다시 동기화할 수 있다.
- Explore Gangneung은 `recodate_places.db`에 데이터가 있으면 관광공사 장소를 Google/TMAP 후보와 자동으로 합치며, DB 파일 수정 시각을 캐시 키에 포함해 동기화된 데이터를 자동으로 다시 읽는다.
- 관광공사 DB, Google Places, TMAP 후보를 합쳐 중복 제거한 결과 강릉 전체/전체 기준 총 1,758개, 12개씩 147페이지, 첫 로딩 약 2.69초를 확인했다. 이 중 관광공사 데이터는 766개가 최종 후보에 포함됐다.
- 코스 흐름과 추천 결과의 장소 순서 변경은 드래그로 가능하며, 삽입 위치가 더 잘 보이도록 후보 자리 사이가 벌어지는 효과를 추가했다.
- 시작 장소를 비워두고 추천지역이 강릉 전체이면 강릉 중심 고정이 아니라 경포, 주문진, 안목·송정, 교동·시내, 정동진 중 하나를 랜덤 기준으로 추천한다.
- 시작 장소 입력칸은 직접 입력하는 칸이 아니라 클릭하면 시작 장소 선택 모달이 열리는 선택 필드로 동작한다.

### 전국 단위 확장 / Explore Korea / ODsay 대중교통 연동

- 기존 강릉 중심 MVP를 전국 단위 추천 구조로 확장했다.
- 메인 화면 문구를 강릉 고정 표현에서 전국 데이트 큐레이션 흐름으로 바꿨다.
- 추천지역은 더 이상 선택사항이 아니라 전국 서비스 기준 필수 조건으로 정리했다.
- 추천지역 선택 모달은 시도 → 시군구 → 읍면동 순서로 선택할 수 있게 구성했다.
- 서울처럼 하나의 광역시 단위는 전체 선택을 허용하고, 경기·충남처럼 넓은 도 단위는 전체 선택보다 시군구/읍면동 선택을 우선하도록 정리했다.
- 읍면동 단계에서는 `부여군 전체로 추천받기`처럼 해당 시군구 전체 선택도 가능하게 했다.
- 지역 상세 선택 화면에서 `충남 시군구 목록` 같은 목록 복귀 버튼이 먼저 보이고, `부여군 전체로 추천받기` 같은 전체 선택 버튼은 목록 아래에 보이도록 위치를 변경했다.
- Explore Gangneung을 Explore Korea로 확장했다.
- Explore Korea에는 전국과 17개 시도 버튼을 추가했다.
- 전국 버튼은 바로 대한민국 전체 기준 `Top 100` 장소를 보여준다.
- 시도 버튼을 누르면 바로 카테고리로 넘어가지 않고, 추천조건의 지역 선택과 같은 상세 지역 선택 모달이 먼저 열린다.
- 상세 지역을 선택한 뒤 카테고리를 고르면 해당 지역/카테고리의 `Top 50` 장소를 보여준다.
- 예를 들어 `서울 → 강남구 → 개포1동 → 카페`를 선택하면 `서울 강남구 개포1동 카페 Top 50` 목록이 열린다.
- Explore Korea 목록은 장소 사진을 목록에서 바로 불러오지 않고, 장소명, 카테고리, 리뷰 수, 영업 상태, 찜, 검색 버튼을 먼저 보여준다.
- 장소 상세창에서 지도와 사진을 보여주며, 사진은 네이버 이미지 검색을 우선 사용하고 실패 시 Google 사진 또는 기존 fallback을 사용한다.
- 추천 결과 카드, 시작 장소 후보, 코스 흐름 장소 사진도 네이버 이미지를 우선 시도하고, 실패 시 Google/TourAPI 계열 fallback을 사용하도록 정리했다.
- 모바일에서 TMAP 정적 지도 이미지가 실패할 때 빈 화면처럼 보이지 않도록 fallback 처리를 추가했다.
- 모바일 화면에서 체크박스가 세로로 깨지거나 카드가 가로로 넘치는 문제를 보정했다.
- 모바일 지역/카테고리 카드는 2열 중심으로 안정적으로 표시되도록 조정했다.
- 모바일 place detail의 지도/사진이 화면 밖으로 튀지 않도록 폭과 비율을 제한했다.

대중교통 연동:

- 기존 대중교통 로직은 `gangneung_bus.db`에 들어 있는 강릉 버스 DB를 우선 탐색하고, 다른 지역은 버스/지하철 추정 안내로 대체하는 구조였다.
- 전국 단위에서는 이 방식으로 실제 버스·지하철 경로를 계산할 수 없기 때문에 ODsay 전국 대중교통 API를 추가했다.
- `backend/app/services/odsay_client.py`를 새로 추가했다.
- `.env`에 `ODSAY_API_KEY`, `ODSAY_REFERER` 값을 추가했다.
- `backend/app/config.py`에 ODsay 설정을 추가했다.
- 대중교통 경로 계산 순서를 `ODsay 실제 전국 경로 → 기존 강릉 버스 DB → 추정 안내 fallback`으로 변경했다.
- ODsay 응답에서 버스, 지하철, 도보 구간, 총 거리, 총 시간, 결제 요금을 읽어 RecoDate의 route leg 형식으로 변환한다.
- ODsay에서 내려주는 실제 교통비를 추천 예산의 교통비에 반영한다.
- ODsay API가 실패하거나 경로가 없으면 기존 fallback 로직을 유지해 추천 기능이 중단되지 않게 했다.
- ODsay URI용 키는 백엔드 호출 시 `Referer` 헤더가 필요해서 `ODSAY_REFERER=http://localhost:5174` 형태로 등록해 사용한다.
- 나중에 `recodate.com`으로 배포하면 `.env`의 `ODSAY_REFERER`를 `https://recodate.com`으로 변경하고 ODsay 콘솔에도 `recodate.com`을 URI로 등록해야 한다.
- `backend/app/main.py`의 선택 코스 실제 경로 계산 설명도 ODsay 전국 버스·지하철 경로 우선 사용으로 수정했다.

- 테스트 결과 예시: 거리 약 13.54km, 시간 38분, 요금 1,650원, source `odsay`, fallback `false`.

- 전국 Top 100 품질 보정: 자체 DB 장소에 외부 리뷰 수가 없을 때 가나다·알파벳순으로 정렬되던 문제를 수정했다. 전국 `전체` 첫 화면은 RecoDate 대표 장소 목록을 우선 사용해 `N서울타워`, `경복궁`, `광장시장`, `제주동문시장`, `감천문화마을`, `해운대해수욕장`, `전주한옥마을`, `불국사`, `성산일출봉`, `롯데월드`, `에버랜드`, `캐리비안 베이` 순으로 안정적으로 반환한다. 이후 장소는 관광공사 출처, 관광명소·테마파크·시장·궁궐 등 장소 성격, 한글 장소명, 주소 완성도를 반영해 정렬한다.
- Top 100 불필요 조회 제거: 전국 `전체`는 관광지 중심 목록이라 최종 결과에 소상공인 관광지 후보를 사용하지 않는데도 17개 전국 중심점에서 272만 건 상가 DB를 조회하던 부분을 제거했다. 서비스 재시작 직후 공개 API 기준 Top 100 첫 12곳 `0.48초`, 서울 지도 100곳 `0.45초`, `캐리비안베이` 검색+주변 91곳 `0.38초`, 상태 확인 `0.04초`를 확인했다.
