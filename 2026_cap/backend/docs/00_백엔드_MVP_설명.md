# 백엔드 MVP 설명

이 문서는 RecoDate MVP 백엔드의 목적과 현재 구현 범위를 설명한다.

## 목적

이 백엔드는 TMAP API로 시작 장소 주변의 장소와 도보·자차 경로를 검색한다. 대중교통 구간은 국토교통부 TAGO 데이터로 만든 강릉 버스 SQLite를 조회해 사용자의 이동수단과 상세 조건에 맞는 데이트 코스를 추천한다.

## 현재 구현 API

| API | 설명 |
|---|---|
| `GET /` | 서버 상태 확인 |
| `GET /api/places/search` | TMAP POI 통합검색으로 시작 장소 후보 검색 |
| `POST /api/recommendations` | 도보/대중교통/자차 조건에 맞는 추천 코스 후보 생성. 경로 API 호출 없음 |
| `POST /api/routes/selected-course` | 선택한 코스의 도보·자차는 TMAP, 버스는 강릉 SQLite에서 계산 |

## 현재 MVP 입력 조건

| 조건 | 반영 여부 |
|---|---|
| 시작 장소 | 반영 |
| 이동수단 | 반영 |
| 빠른 추천/상세 설정 | 반영 |
| 음식 종류 | 상세 설정에서 반영 |
| 이동 반경 | 상세 설정에서 반영 |
| 추천 코스 개수 | 최대 5개까지 반영 |
| 시작/종료 시간 | 보류 |
| 예산 | SQLite 공식 가격 우선 반영, 미등록 장소는 카테고리 대표값으로 보완. 버스·필수 택시·자차 연료비 포함 |
| 운영시간 | 보류 |

## 추천 방식

~~도보:

```text
장소 A → 장소 B
장소 B → 장소 C
장소 C → 장소 D
```

각 구간을 보행자 경로 API로 계산한 뒤 합산한다.~~

~~자차:

```text
출발지 + 경유지 + 목적지
```

자동차 다중경유지 API로 전체 경로를 한 번에 계산한다.~~

변경:
추천 목록 생성 단계에서는 TMAP 경로 API를 호출하지 않는다.
장소 좌표의 직선거리를 이용해 예상 거리와 예상 시간을 계산한다.
사용자가 추천 카드 중 하나를 선택한 뒤에만 실제 도보, 대중교통 또는 자차 경로를 계산한다.

대중교통 모드는 장소 사이 직선거리가 800m 이하이면 보행자 경로 API를 사용한다. 더 긴 구간은 강릉 버스 SQLite에서 인근 정류장을 찾고, 직행 노선을 먼저 탐색한 뒤 없으면 1회 환승 노선을 탐색한다. DB에 노선 데이터가 없거나 경로를 찾지 못하면 긴 구간은 예상값으로 대체한다.

추천 코스는 `출발지 → 음식점 → 카페 → 액티비티 → 마무리 산책` 순서로 구성한다. 액티비티 슬롯은 해변, 영화관, 박물관, 미술관을 우선 검색하고 마무리 슬롯은 거리, 공원, 해변을 검색한다.

변경 이유:
추천 후보마다 경로 API를 호출하면 API 사용량이 과도하게 증가한다.
특히 도보는 장소 5개 코스 기준으로 후보 1개당 4회 호출이 필요하므로, 추천 단계와 실제 경로 계산 단계를 분리한다.

~~선택한 자차 코스는 자동차 다중경유지 API로 한 번에 계산한다.~~

변경:
이 차량 이어 붙이기 버전에서는 선택한 자차 코스도 일반 자동차 경로안내를 구간별로 호출한다.
예를 들어 장소가 5개이면 `1번 → 2번`, `2번 → 3번`, `3번 → 4번`, `4번 → 5번` 총 4개 구간을 계산하고 결과를 합산한다.

변경 이유:
자동차 다중경유지는 호출 1회로 전체 경로를 받을 수 있지만 일 사용 한도가 낮다.
MVP에서 여러 번 테스트해야 하는 상황에서는 자동차 경로안내 구간별 호출 방식이 한도 관리와 오류 추적에 더 유리하다.
