# 코드파일 역할 설명

이 문서는 RecoDate MVP 백엔드 코드 파일의 역할을 설명한다.

## 파일별 역할

| 파일 | 역할 |
|---|---|
| `app/main.py` | FastAPI 앱 진입점, API 라우터 정의 |
| `app/config.py` | `.env` 로딩과 기본 설정값 관리 |
| `app/schemas.py` | 요청/응답 데이터 구조 정의 |
| `app/services/tmap_client.py` | TMAP API 호출 담당 |
| `app/services/tago_client.py` | 국토교통부 TAGO 버스 정류장·노선·도착 정보 호출 담당 |
| `app/services/gangneung_bis_client.py` | 강릉 BIS 공개 지도에서 노선 목록과 정류장 좌표 조회 |
| `app/services/bus_repository.py` | 강릉 버스 SQLite에서 직행·1회 환승 경로 탐색 |
| `app/services/recommendation_service.py` | 추천 후보 검색, 지역 특화 조합 생성, 예상 거리/시간·예산 계산, 선택 코스 실제 경로 계산 담당 |
| `app/services/price_repository.py` | SQLite에서 장소별 공식 가격 조회 |
| `scripts/seed_price_db.py` | 공식 가격표 SQLite 생성 |
| `scripts/seed_bus_db.py` | CSV와 TAGO API를 이용해 강릉 버스 SQLite 생성 |

## 실행 흐름

```text
프론트엔드 또는 Swagger
→ app/main.py
→ RecommendationService
→ TmapClient
→ TMAP API
→ 추천 결과 반환
```

추천 목록 생성 단계:

```text
프론트엔드 또는 Swagger
→ POST /api/recommendations
→ TMAP 주변 POI 검색
→ 좌표 기반 예상 거리/시간 계산
→ 추천 카드 반환
```

선택 코스 실제 경로 계산 단계:

```text
프론트엔드 또는 Swagger
→ POST /api/routes/selected-course
→ 도보·자차는 TMAP 경로 API 호출
→ 대중교통은 강릉 버스 SQLite에서 직행 또는 1회 환승 탐색
→ 실제 경로 반환
```

## 입력값

추천 생성 API는 다음 값을 받는다.

- 시작 장소
- 이동수단
- 추천 방식
- 이동 반경
- 추천 코스 개수
- 음식 종류

## 출력값

추천 결과에는 다음 값이 포함된다.

- 추천 코스 ID
- 추천 제목
- 장소 목록
- 장소 순서
- 총 이동거리
- 총 이동시간
- 실제 경로 좌표
- API 호출 수
- 추천 이유

추천 생성 API의 `api_call_count`는 0이다.
~~실제 경로 API의 `api_call_count`는 도보일 때 구간 수, 자차일 때 1이다.~~

변경:
이 차량 이어 붙이기 버전에서는 실제 경로 API의 `api_call_count`가 도보와 자차 모두 실제 호출한 구간 수이다.
동일 좌표처럼 5m 미만인 구간은 API를 호출하지 않고 0m/0초 구간으로 처리한다.

변경 이유:
자차도 일반 자동차 경로안내를 구간별로 호출하도록 바뀌었기 때문에, 호출 수를 1로 고정하면 실제 사용량을 확인하기 어렵다.

~~실제 경로 API는 실제 거리와 시간만 반환한다.~~

변경:
실제 경로 API는 TMAP 길찾기 응답의 `features[].geometry.coordinates`를 추출해 `path` 좌표 목록도 함께 반환한다.

변경 이유:
프론트엔드 TMAP 지도 SDK에서 장소 좌표 직선이 아니라 실제 도보/자동차 경로선을 표시하기 위해 필요하다.

~~추천 후보 조합이 0개이면 그대로 빈 결과를 반환한다.~~

변경:
추천 후보 조합이 0개이면 자동으로 완화 조건을 적용한다. 완화 조건에서는 도보 반경을 최대 3km까지 넓히고, 시작 장소-음식점 / 음식점-카페 최소 거리 조건을 50m에서 10m로 낮춘다.

변경 이유:
강릉중앙시장처럼 장소가 밀집된 지역은 좋은 후보가 있어도 기존 50m 필터 때문에 모든 조합이 탈락할 수 있다. MVP에서는 사용자가 결과를 전혀 받지 못하는 것보다, 완화 조건을 적용해 후보를 먼저 보여주는 편이 낫다.

~~TMAP 주변 검색 카테고리 중 하나가 비정상 응답을 주면 추천 API 전체가 실패한다.~~

변경:
TMAP 주변 검색 카테고리 하나가 JSON이 아닌 응답을 주거나 실패해도 해당 카테고리만 건너뛰고 나머지 후보로 추천을 계속 진행한다.

변경 이유:
특정 장소와 카테고리 조합에서 TMAP이 빈 응답 또는 비JSON 응답을 줄 수 있다. 이때 전체 추천 API가 죽으면 사용자가 원인을 이해하기 어렵기 때문에, 실패한 카테고리는 제외하고 가능한 후보로 추천을 이어간다.

## 현재 한계

- 공식 가격이 등록된 장소는 SQLite 값을 반영하고, 미등록 장소는 카테고리 대표값을 사용한다.
- 시작/종료 시간은 반영하지 않는다.
- 운영시간은 반영하지 않는다.
- 장소 품질 점수는 아직 단순하다.
- 자유 편집 API는 아직 만들지 않았다.
