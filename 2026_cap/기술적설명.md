# RecoDate 기술적 설명

이 문서는 RecoDate MVP가 어떤 외부 API와 내부 데이터를 사용하고, 데이트 코스 추천이 어떤 흐름으로 생성되는지 정리한다. API 키와 비밀번호 같은 민감 정보는 문서에 포함하지 않는다.

## 1. 전체 구조

RecoDate는 정적 프론트엔드와 FastAPI 백엔드로 구성되어 있다.

- 프론트엔드: `frontend/index.html`, `frontend/app.js`, `frontend/styles.css`
- 백엔드: `backend/app/main.py`
- 추천 핵심 로직: `backend/app/services/recommendation_service.py`
- 인증/회원: `backend/app/services/auth_repository.py`
- 서버 배포 경로: `/opt/recodate`
- 운영 방식: Nginx가 프론트엔드 파일을 제공하고 `/api` 요청을 FastAPI 백엔드로 프록시한다.
- 백엔드 실행: `systemd`의 `recodate.service`가 `uvicorn app.main:app --host 127.0.0.1 --port 8010`을 실행한다.

## 2. 사용 API와 역할

### TMAP API

TMAP은 장소 검색, 도보 경로, 자동차 경로, 정적 지도 이미지, 지도 SDK에 사용된다.

- 주변 장소 검색: `TmapClient.search_around()`
- 키워드 장소 검색: `TmapClient.search_pois()`
- 도보 경로: `TmapClient.route_pedestrian()`
- 자동차 경로: `TmapClient.route_car()`
- 대중교통 경로 보조: `TmapClient.route_transit()`
- 정적 지도 이미지: `TmapClient.static_map_image()`
- 지도 SDK 키 전달: `/api/config/tmap-sdk`

프론트엔드에서는 TMAP JavaScript SDK를 사용해 선택한 코스의 마커와 경로선을 표시한다. SDK 로딩이 실패하거나 모바일 환경에서 제약이 생기면 백엔드의 정적 지도 이미지와 SVG 오버레이로 fallback한다.

### ODsay 대중교통 API

ODsay는 대중교통 길찾기의 1차 경로 계산 API로 사용된다.

- 대중교통 경로 검색: `searchPubTransPathT`
- 노선 좌표 로딩: `loadLane`
- 구현 위치: `backend/app/services/odsay_client.py`

`searchPubTransPathT`에서 추천 경로 후보를 받고, 가장 시간이 짧은 경로를 선택한다. 이후 응답의 `info.mapObj`를 `loadLane`에 전달해 버스/지하철 노선 좌표(`graphPos`)를 받아 지도 경로선으로 사용한다. ODsay의 `loadLane`은 `mapObject` 앞에 `0:0@` 접두사를 붙여야 정상적으로 노선 그래픽 데이터를 반환한다.

ODsay가 실패하면 TMAP 대중교통 API를 보조로 시도하고, 그것도 실패하면 내부 예상 경로 또는 버스 저장소 기반 fallback을 사용한다.

### Google Places API

Google Places는 장소 품질 보강과 사진/리뷰 정보 확보에 사용된다.

- 주변 장소 검색: `GooglePlacesClient.search_nearby()`
- 텍스트 기반 사진 검색: `GooglePlacesClient.search_photo_by_name()`
- 사진 미디어 호출: `GooglePlacesClient.get_photo()`

추천 후보에는 Google 평점, 리뷰 수, Google Maps 링크, 운영시간, 사진 메타데이터가 붙는다. 정렬 시 리뷰 수와 평점은 장소 품질 점수에 반영된다.

### 네이버 검색 API

네이버 API는 국내 사용자가 알아보기 쉬운 리뷰순 보강과 이미지 보강에 사용된다.

- 네이버 지역 검색: `NaverLocalClient.search_popular()`
- 네이버 이미지 검색: `NaverLocalClient.search_image()`

장소 목록에는 네이버 리뷰순 매칭 결과가 `naver_popular`, `naver_popularity_rank`로 반영된다. 상세 화면의 사진은 가능한 경우 네이버 원본 이미지 링크를 먼저 사용하고, 실패하면 네이버 썸네일 또는 Google/관광공사 사진으로 fallback한다.

### 한국관광공사/관광 데이터

관광지 데이터와 사진 데이터는 관광/문화/산책 후보 보강에 사용된다.

- 관광 장소 저장소: `TourPlaceRepository`
- 관광 사진 검색: `TourPhotoClient`
- 관광 콘텐츠 클라이언트: `TourContentClient`

Google/TMAP 결과가 부족한 지역 또는 관광 카테고리에서는 내부 SQLite 형태의 관광 장소 데이터와 관광공사 사진을 보조로 사용한다.

### 행정동 데이터

행정구역 선택과 지역 제한 추천에는 `frontend/assets/korea_admin_regions.json`을 사용한다.

이 파일에는 시도, 시군구, 읍면동의 키, 이름, 중심 좌표가 들어 있다. 백엔드는 이 데이터를 읽어 `sido_`, `sgg_`, `emd_` 키를 해석하고, 장소 좌표가 어느 행정동에 가장 가까운지 계산해 필터링한다.

## 3. 추천 요청 흐름

사용자가 추천 조건을 입력하면 프론트엔드는 `/api/recommendations`로 요청을 보낸다.

주요 입력값은 다음과 같다.

- 시작 장소
- 추천 지역 키: 예 `sido_11`, `sgg_11680`, `emd_1168066000`
- 이동수단: 도보, 대중교통, 자차
- 빠른 추천/상세 설정
- 음식 종류, 점심/카페/저녁/술집 포함 여부
- 숙박 여부와 숙소
- 꼭 들를 장소
- 근처 동 포함 여부
- TripTI 선호 카테고리

백엔드는 요청을 받은 뒤 다음 순서로 코스를 만든다.

1. 시작 장소를 기준점으로 정규화한다.
2. 선택한 지역 키로 행정구역 필터를 만든다.
3. 음식점, 카페, 액티비티, 마무리/산책 장소 후보를 수집한다.
4. Google Places, TMAP, 관광공사/내부 데이터, 네이버 리뷰순 정보를 합쳐 후보를 보강한다.
5. 구/동 선택 시 후보 장소를 행정구역 기준으로 강하게 필터링한다.
6. 점심, 카페, 액티비티, 마무리 장소를 조합해 코스 후보를 만든다.
7. 상세 설정에 따라 저녁, 술집, 숙소, 꼭 들를 장소를 코스에 추가한다.
8. 이동수단별 예상 경로와 예산을 계산한다.
9. 점수화 후 중복이 적은 코스를 최종 선택한다.

## 4. 지역 필터링 원칙

RecoDate의 지역 추천 원칙은 다음과 같다.

- 시도 선택: 해당 시도 안의 장소만 후보로 사용한다.
- 시군구 선택: 해당 시군구 안의 장소만 후보로 사용한다.
- 읍면동 선택: 기본적으로 해당 동 안의 장소만 후보로 사용한다.
- `근처 동까지 코스에 포함시키기`가 켜져 있으면 같은 구 안의 인접 동을 후보에 포함한다.
- 구/동 기준 추천에서 후보가 부족해 fallback이 발생하더라도 최종 후보는 다시 행정구역 필터를 통과해야 한다.

행정구역 판정은 실제 폴리곤 경계가 아니라 현재 MVP에서는 각 행정동 중심 좌표와 장소 좌표의 최단거리로 근사한다. 따라서 경계선 근처 장소는 인접 동으로 분류될 수 있다. 향후 정확도를 높이려면 행정구역 폴리곤 데이터를 추가해 point-in-polygon 방식으로 판정하는 것이 좋다.

## 5. 코스 후보 생성 방식

추천 서비스는 역할별 후보 그룹을 만든다.

- 음식점: 한식, 중식, 일식, 양식, 패스트푸드, 기타 음식
- 카페: 카페/디저트
- 액티비티: 야외 액티비티, 실내 액티비티, 문화/전시
- 마무리: 공원, 산책로, 전망대, 거리
- 선택 옵션: 저녁, 술집, 숙소, 필수 방문 장소

후보 그룹은 거리, 리뷰 수, 평점, 네이버 리뷰순, 카테고리 적합도를 기준으로 정렬된다. 이후 조합을 만들 때 너무 가까운 중복 장소나 시작 장소와 사실상 같은 장소는 제외한다.

## 6. 점수화 메커니즘

추천 점수는 다음 요소를 함께 고려한다.

- 이동수단에 적절한 총 이동 거리와 시간
- 장소 간 거리가 너무 멀거나 너무 가까운지 여부
- Google 리뷰 수와 평점
- 네이버 리뷰순 매칭 여부
- 필수 장소 포함 여부
- 카테고리 다양성
- TripTI 선호 카테고리와의 일치도
- 술집/숙박/저녁 등 상세 옵션 반영 여부

최종 결과는 점수순으로 정렬하되, 같은 장소 조합이 반복되지 않도록 다양한 코스를 우선 선택한다.

## 7. 경로 계산 방식

### 도보

짧은 구간은 TMAP 보행자 경로 API를 사용한다. 응답의 경로 좌표를 지도에 표시하고, 실패하면 장소 간 직선 fallback을 사용한다.

### 자차

TMAP 자동차 경로 API를 사용한다. 총 거리와 예상 시간을 받아 코스 요약과 예산 계산에 반영한다.

### 대중교통

대중교통은 ODsay를 우선 사용한다.

1. ODsay `searchPubTransPathT`로 경로 후보를 검색한다.
2. 가장 시간이 짧은 경로를 선택한다.
3. `info.mapObj`를 `0:0@...` 형태로 보정해 `loadLane`에 전달한다.
4. `graphPos` 좌표를 지도 경로선으로 사용한다.
5. 각 구간에는 출발 정류장/역, 도착 정류장/역, 노선명, 정거장 수를 안내 문구로 표시한다.

ODsay 실패 시 TMAP 대중교통, 내부 버스 저장소, 예상 경로 순으로 fallback한다.

## 8. 장소 상세와 사진 처리

장소 상세 화면은 지도, 사진, 리뷰 수, 운영시간, 네이버 검색, 찜하기, 이 장소로 코스 추천받기 기능을 제공한다.

사진은 다음 우선순위로 표시한다.

1. 네이버 이미지 원본 링크
2. 관광공사/내부 관광 사진
3. Google Places 사진
4. 네이버 썸네일 fallback

원본 이미지가 외부 서버에서 차단되거나 깨지면 썸네일로 대체한다.

## 9. 저장 기능

로그인 사용자는 다음 데이터를 저장할 수 있다.

- 찜한 장소
- 저장한 코스
- 최근 본 장소

회원 인증은 FastAPI 백엔드에서 처리하며, 프론트엔드는 토큰을 저장해 API 요청 시 인증 헤더로 전달한다.

### 일반 이메일 계정

일반 계정은 이메일 기반 로그인으로 동작한다. 회원가입 시 사용자는 이메일, 비밀번호, 비밀번호 확인, 닉네임, 전화번호, 필수 약관 동의, 만 14세 이상 확인을 입력한다.

- 로그인 식별자: 이메일
- 비밀번호 저장: 원문 비밀번호를 저장하지 않고 `PBKDF2-HMAC-SHA256` 해시와 salt를 저장한다.
- 세션 방식: 로그인 성공 시 임의 토큰을 발급하고 `sessions` 테이블에 만료 시간을 저장한다.
- 중복 방지: 이메일과 전화번호는 중복 가입을 제한한다.

### 카카오 로그인 / 카카오 회원가입

카카오 계정은 비밀번호 없는 소셜 계정으로 처리한다. 사용자는 카카오 인증을 통과한 뒤 RecoDate에서 사용할 닉네임을 별도로 설정한다.

사용 API 흐름은 다음과 같다.

1. 프론트엔드의 `카카오로 시작하기` 버튼이 `/api/auth/kakao/start`를 호출한다.
2. 백엔드는 Kakao OAuth authorize URL로 리다이렉트한다.
3. 카카오 인증 성공 후 `https://recodate.com/api/auth/kakao/callback`으로 인가 코드가 돌아온다.
4. 백엔드는 카카오 토큰 API로 access token을 발급받는다.
5. 백엔드는 카카오 사용자 정보 API `/v2/user/me`로 카카오 회원 ID, 이메일, 프로필 닉네임을 조회한다.
6. 이미 연결된 카카오 회원이면 RecoDate 세션 토큰을 발급한다.
7. 같은 이메일의 기존 RecoDate 계정이 있으면 카카오 ID를 연결하고 로그인 처리한다.
8. 신규 카카오 회원이면 `kakao_signup_pending`에 임시 가입 토큰을 만들고 프론트엔드로 돌려보낸다.
9. 프론트엔드는 닉네임과 필수 동의를 받은 뒤 `/api/auth/kakao/complete`를 호출한다.
10. 백엔드는 비밀번호 없는 `auth_provider='kakao'` 계정을 생성하고 RecoDate 세션 토큰을 발급한다.

카카오 회원은 일반 비밀번호를 입력하지 않으며, 추후 로그인도 카카오 로그인 버튼을 통해 진행하는 것을 기본 원칙으로 한다. 이메일 인증은 카카오가 제공한 이메일을 신뢰하므로 별도로 수행하지 않는다.

## 10. 모바일 대응

모바일에서는 다음 사항을 별도 처리한다.

- 하단 탭 고정
- 지도와 상세 코스 보기 영역의 폭 고정
- 코스 흐름 카드와 대중교통 안내가 화면 밖으로 밀리지 않도록 `min-width: 0`, `overflow-wrap`, 모바일 전용 grid 적용
- 찜한 장소 카드와 유사 장소 카드에서 텍스트와 버튼이 겹치지 않도록 1열 구조 적용

## 11. 배포 구조

현재 운영 서버는 Naver Cloud Ubuntu 서버다.

- 공인 IP: `223.130.153.14`
- 백엔드 포트: `127.0.0.1:8010`
- 외부 공개 포트: HTTP 80, HTTPS 443 예정
- Nginx: 프론트엔드 정적 파일 제공 및 `/api` 프록시
- systemd: 백엔드 프로세스 자동 실행/재시작

도메인을 연결하면 DNS의 A 레코드를 서버 공인 IP로 지정하고, Nginx의 `server_name`을 도메인으로 설정한 뒤 Let's Encrypt 인증서를 발급해 HTTPS를 적용한다.

## 12. 향후 개선 과제

- 행정구역 판정을 중심 좌표 기반에서 폴리곤 기반으로 개선
- TMAP/ODsay 쿼터 관리와 API 장애 시 사용자 메시지 개선
